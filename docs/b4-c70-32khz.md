# The early-BeagleBoard timer freeze: capacitor C70, the 32 kHz oscillator, and `omap3-beagle-ab4.dts`

This is the root-cause writeup for the bug this repo exists to fix.

## Symptom

On an early BeagleBoard (Rev A – B4) running a modern (6.x) mainline kernel, the
board boots fine, then after some time — seconds to tens of minutes, load-dependent —
**everything time-based hangs**: `sleep` never returns, network pings stop after one
packet, the serial console appears frozen (though it still echoes keystrokes). The
wall clock (`date`) keeps advancing.

The tell: in `/proc/interrupts`, the **clockevent** interrupt (GPTIMER1, IRQ 53 /
INTC 37) **stops incrementing** while the free-running 32 kHz **clocksource** keeps
going. The kernel tick is dead, so all `hrtimer`-driven things (sleeps, timeouts,
scheduler ticks) stall — but reads of the clocksource still work, so `date` lies about
being fine.

## Why it happens

The clockevent is **GPTIMER1 clocked from the 32.768 kHz oscillator**. Under load the
timer's counter reload is unreliable: on an overflow it fails to reload the timer
load register (TLDR), so instead of firing again ~10 ms later it free-runs the long
way to its next overflow (tens of minutes / hours away). No overflow → no interrupt →
no tick → freeze.

The reason the **32 kHz** source specifically misbehaves is a **board defect**, not a
CPU bug:

> **BeagleBoard Community wiki, "Boards revision A and < B5":** *"There is some issue
> with a 32 kHz clock… From this e.g. GPIOs, GPTIMERs, and USB on BeagleBoard might be
> affected… the serial console hangs after some time and no serial input/output is
> possible any more. (A) Software workaround: Don't use the 32 kHz timer to clock
> Linux, instead use the MPU timer. (B) Hardware workaround: Remove capacitor C70…
> Board revision ≥ B5 removes capacitor C70."*

Rev A/B boards **have** capacitor **C70**; boards **≥ B5 removed it**. On the affected
boards C70 degrades the 32 kHz clock quality enough to make the 32 kHz-clocked GP timer
hang. (Photo of C70's location: [`beagle-c70-capacitor.jpg`](beagle-c70-capacitor.jpg).)

This was reported by TI/BeagleBoard engineers back in **2008**
("[GPT1 timer issue aka UART3 hang on Beagle Board](https://forum.beagleboard.org/t/gpt1-timer-issue-aka-uart3-hang-issue-on-beagle-board/2962)"),
who observed the exact same "counter reloaded to a random value → no overflow interrupt
→ console hangs on jiffies" behavior, **only on BeagleBoards** (Overo/EVM/Zoom were
fine), and recommended: *"instead of using the 32K timer for GPT1, use the MPU timer."*

## Why it is NOT an OMAP silicon erratum

It is genuinely a **board** issue (a capacitor), so it is **not** in the OMAP3 errata
document **SPRZ278F** (included here as
[`omap-errata-sprz278f.txt`](omap-errata-sprz278f.txt)). That is why searching the
silicon errata for it comes up empty, and why it is BeagleBoard-specific. Confirmed
independently: the **Ångström 3.0.14 (2011)** kernel with the old `omap2_gp_timer`
driver freezes under the same stress, so it is not a 6.x driver regression either — it
is the hardware.

## The fix: `omap3-beagle-ab4.dts`

Mainline Linux ships a device tree specifically for these boards:
`arch/arm/boot/dts/ti/omap/omap3-beagle-ab4.dts` (model *"TI OMAP3 BeagleBoard A to B4"*).
It implements exactly the software workaround (A):

```dts
/* Workaround for capacitor C70 issue, "Boards revision A and < B5" */
&counter32k    { status = "disabled"; };                 /* 32k unusable as clocksource   */
&timer1_target { timer@0 { /delete-property/ ti,timer-alwon; }; };  /* drop 32k GPT1 as clockevent */
&timer12_target{ ti,no-idle; };                          /* clocksource -> timer12 (secure 32k) */
&timer2_target {                                         /* clockevent -> timer2...             */
    timer@0 { assigned-clocks = <&gpt2_fck>;
              assigned-clock-parents = <&sys_ck>; };      /* ...clocked from sys_ck (13 MHz)     */
};
```

So the clockevent moves off the flaky 32 kHz GPTIMER1 onto **GPTIMER2 @ `sys_ck`
(13 MHz on this board = 26 MHz osc / 2)** — ~400× faster and, more importantly, on a
reliable clock. The clocksource moves to GPTIMER12.

**No kernel source patch is required for the timer fix** — you just build and boot
`omap3-beagle-ab4.dtb` instead of `omap3-beagle.dtb`. This repo's kernel build produces
that DTB.

### Verifying the fix at boot

The kernel log should show the clockevent on GPTIMER2 (`@49032000`) at 13 MHz, not
GPTIMER1 (`@48318000`) at 32768 Hz:

```
OF: fdt: Machine model: TI OMAP3 BeagleBoard A to B4
TI gptimer clockevent: 13000000 Hz at /ocp@68000000/target-module@49032000
TI gptimer clocksource: always-on /ocp@68000000/target-module@48304000
clocksource: Switched to clocksource dmtimer
```

Stress test (should run indefinitely; the un-fixed board wedges within minutes):

```sh
for i in 1 2 3 4 5 6 7 8; do ( while true; do sleep 1; done ) & done
sleep 5 ; echo alive ; date        # repeat; must keep printing "alive"
```

Verified stable for 8h+ under this hammer on the fixed DTB.

## Dead ends (for the record)

These were tried and are **not** the fix (they only shifted the freeze probability or
targeted the wrong layer):

- Forcing the GPTIMER1 clockevent **non-posted** (`ifctrl=0`) — 10× longer MTTF, not a fix.
- **Stop-before-reload** in `dmtimer_set_next_event` — periodic mode still froze, proving
  it isn't a reprogram race.
- `nohz=off highres=off` (periodic tick) — survives longer but still wedges (~38 min).
- Disabling cpuidle deep C-states, `ti-sysc` runtime PM — froze regardless.
- U-Boot poking `CM_CLKSEL_WKUP` (0x48004c40) — Linux re-selects the 32 kHz parent early,
  so only the DTB (`ab4`) actually moves the clockevent.
